## Entry 4 — Visual identity: brand kept, feel flagged as a poor fit

User directive: *"keep the brand/logo, rethink the feel ONLY if you think it's not a great fit. if not, just fix the system."*

**Facilitator verdict: the feel is not a great fit.** Evidence gathered from `packages/shared/src/styles/tokens.css` and the desktop source:

1. **The palette is verbatim default shadcn slate + indigo.** `--primary: #4F46E5` (indigo-600) over `#0F172A` / `#1E293B` / `#F1F5F9` slate. This is the most common AI-scaffold palette in existence — zero ownership, and it reads "developer dashboard" against a product promising calm and relief.
2. **Money is set in JetBrains Mono.** `font-mono` appears 62 times across 39 files, including `MoneyInput`, `AccountRow`, `AssetRow`, `ExpenseList`, `DashboardMetricCard`, `CashFlowSummaryCard`, `NetWorthBreakdownBar`. A *code* font on every dollar figure — the single strongest mis-signal in the app for the Marie audience. Meanwhile `tabular-nums` appears only 9 times (6 of them in Car), so numeric alignment is being bought with a code font instead of tabular figures.
3. **Status and identity share a color family.** `--chart-1` === `--primary` (#4F46E5) and `--chart-4` === `--destructive` (#F43F5E) — so "on track" renders in brand purple and an ordinary spending category renders in the error color. Not repairable by a type scale; requires palette restructure.
4. **Light mode is the default path** (`defaultTheme="system"` in `main.tsx:22`) yet ships a **dark slate sidebar (`--sidebar: #1E293B`) against white content** — a split-personality shell, and another dev-tool signature.
5. **Card is indistinguishable from its container in both modes.** Light: `--card` and `--background` are both `#FFFFFF`. Dark: `--card` and `--muted` are both `#1E293B`.
6. **No type, spacing, shadow, or chart-palette scales exist at all** — only colors, two font families, and one radius.

- **Decision:** Keep the Nixus logo and indigo as the brand/action color. Rethink surfaces, typography, and status color as a scoped re-feel, not a rebrand. Colour/surface direction to be **chosen by the user**, not authored by the facilitator.

## Entry 5 — Money typography

- **Decision:** Money renders in **Inter with tabular figures** (`font-feature-settings: "tnum"`), not JetBrains Mono.
- **Supersedes:** `ux-design-specification.md` documents "monospace financial figures" as an explicit table convention. That decision is retired — it was buying column alignment with a code font. Tabular figures buy the same alignment without the developer-tool signal.
- **Migration:** 62 `font-mono` usages across 39 files. Mono is retained only for genuinely code-like content (none currently identified in Finance).
- **Source:** User confirmation, 2026-08-01.

## Entry 6 — Brand color contradiction resolved: the logo is the source of truth

Three artifacts disagreed about the accent color:

The token layer was never authoritative because it never agreed with the written spec.
- **Decision:** **The logo is the source of truth.** The Nixus identity is the periwinkle→violet→pink gradient. "Teal" is retired from all specs and code. `#818CF8` (already the dark-mode `--primary`) becomes the brand anchor in both modes rather than the harsher `#4F46E5`.

## Entry 7 — IA: the target structure already exists as invisible grouping

`InnerTabNav.tsx` already groups the 10 Finance tabs into **four divider-separated clusters**:

```
Dashboard │ Budget · Income · Recurring │ Accounts · Assets · Net Worth │ Spending Trends · Year Summary · Projection
```

- **Finding:** This is very nearly the four-destination IA the review proposed (Today / Spending / Wealth / Insights). The correct structure was already discovered by whoever built the nav — it was expressed as *visual grouping* rather than promoted to *actual navigation*, so the user still pays a 10-item scan cost.
- **Decision:** Promote the existing clusters to first-class destinations. This is a re-labelling and route-nesting exercise, not an IA invention. Cluster membership is preserved; `Recurring` stays with Budget/Income, `Projection` stays with the analysis group.
- **Binding constraint discovered (architecture D8):** *"no new top-level sidebar or InnerTabNav item"* — new features must nest under an existing section via layout route + segmented sub-nav (the `/net-worth` → `/net-worth/financial-health` pattern). This **forbids** adding Transactions as an 11th tab, and instead mandates it as a segmented sub-nav inside the Spending destination. The constraint and the recommendation agree.

## Entry 9 — Status vocabulary already canonical in the codebase

- **Decision:** Reuse this vocabulary verbatim. The review's suggested "Upcoming" is **retired** in favour of `due_soon` / `projected_due`. Do not invent new status words.

## Entry 10 — Hard constraints carried into both spines

- **Window:** default 1280×800, **minimum 1024×680** (`tauri.conf.json`). Every layout must hold at 1024px wide.
- **Privacy:** all figures route through the global `hide_values` mask; backend always returns raw cents, frontend masks. No figure may bypass it.
- **Financial health is a lagging indicator** — trailing averages over *completed* months, excluding the current partial month. UI must state this; must never imply live/real-time.
- **Educational-not-advice disclaimer** is permanent, always-visible UI. Not dismissible fine print.
- **`data_sufficient: false`** is a first-class UI state, not an error.
- **Waterfall logic must never be re-derived in the frontend** — render `current_step` only.
- **AI failure never blocks the task.** Manual fallback always visible/reachable; all AI errors carry `recoverable: true`.
- **Loading:** per-card skeletons, never a global spinner. **Errors:** inline, never modal (except destructive confirms).
- **Tray:** app hides to tray on window close; first-run must explain this. Required onboarding message.
- **Recurring- and import-generated expenses carry no `account_id`** even though manual ones can. UI must distinguish "no account chosen" from "this source can't link yet."
- **Net worth history is discrete event-driven snapshots**, not a continuous timeline. Charts must not imply daily tracking.
- **No FX conversion anywhere** — CAD and USD coexist unconverted.

## Entry 14 — Budget zero-state: three paths, one portable format

- **Decision:** Ship **both** seeding paths, and design the template format for **future community sharing** from day one.
  1. **AI-derived (happy path)** — first import → AI categorizes → *"Here's a budget based on what you actually spent. Adjust anything?"* Zero manual entry.
  2. **Starter templates (AI-less path)** — Renter / Homeowner / Homeowner with car. ~12 pre-filled Canadian categories, editable targets, one confirm. **Required**, because AI is bring-your-own-key: a user with no credentials must still reach a budget in ~2 clicks.
  3. **Start from scratch** — retained as the secondary path for Dev.
- **Forward-looking requirement (user, 2026-08-01):** *"In the future, I would like to have community-led templates that people can share."*
  - **Consequence for this spec:** the starter template must be a **portable, versioned, human-readable document** (schema + `version` field), not hardcoded seed logic in Rust. Import/export of a template file must be designed now even if the sharing UI ships later — retrofitting a format after templates are hardcoded is the expensive path.
  - Sharing itself is **out of scope** for this run; the format and an import-from-file affordance are **in scope**.
  - Local-first constraint holds: template sharing must never require an account or a server. File-based exchange only.

## Entry 19 — Contrast verified computationally; chart ramp corrected

Every token pair was checked with a WCAG relative-luminance script rather than asserted. **Three real failures were found in the first draft of this spine and fixed:**

1. **`chart-4`, `chart-5`, `chart-8` failed 3:1 in light mode** (2.76, 2.60, 2.57 on `card`).
2. **`ink-faint` failed 4.5:1 in both modes** (3.10 light, 3.51 dark). It is used for table column heads and axis ticks, which are content, not decoration — so it was darkened rather than exempted. Final: `#7A7167` light (4.79 on card, 4.52 on page), `#8D8478` dark (4.51 on card).
3. **The bigger flaw — adjacent chart steps had near-identical luminance.** Walking the logo gradient smoothly produced neighbours differing in hue but not lightness: measured adjacent separation was as low as **1.00:1** between `chart-4` and `chart-5`. That reproduces the exact "two indistinguishable purples" defect the eight-step ramp was created to fix, and fails outright for a colorblind user.

**Correction:** the ramp now **alternates luminance** — odd steps dark (4.35–5.70:1 on card), even steps light (≥3.15:1). Verified: every step **≥3.15:1** against `card`, every adjacent pair **≥1.37:1** against each other, in both modes.

Two constraints this introduces, now recorded in the spine: charts must sit on `{colors.card}` (the ramp is verified against card, not page), and **segment order matters** — `chart-3` and `chart-7` share a luminance and are separated by hue alone, so they must never be adjacent.

Final state: **all 73 tokens pass** — text ≥4.5:1 on both card and page in both modes, badge ink ≥4.5:1 on badge background, chart steps ≥3.0:1 with ≥1.35:1 adjacent separation.

For the record, the tokens this replaces: `text-emerald-600` measured **3.88:1** and `text-teal-700` **2.67:1** on the old dark card `#1E293B`.

## Entry 22 — Reviewer gate: three lenses, 72 findings

Ran rubric walker + accessibility audit + Marie persona lens as parallel subagents. Reports at `review-rubric.md`, `review-accessibility.md`, `review-marie.md`; consolidated at `validation-report.html` / `.md`.

## Entry 23 — Two reviewer fixes rejected on computational evidence

Both were tested before being accepted, and both were wrong. The replacements are structural rather than cosmetic.

**1. "Remove the same-luminance chart collision" is impossible at n=8.** An alternating-luminance ramp has four steps in a dark band (~4.5:1) and four in a light band (~3.15:1); any two steps *within* a band necessarily share luminance. Repairing `chart-3`/`chart-7` relocated the collision to `chart-2`/`chart-8` — verified by solving for it. Alternating separation and all-pairs-distinct are mutually exclusive.
→ **Replaced with two binding rules:** colours are assigned by rank order and never pinned to category identity; every stacked or allocation chart draws a 1px `card` divider between segments, giving each a ≥4.5:1 edge against its neighbour regardless of adjacency.

**2. No single focus-ring colour can work in dark mode.** A ring must clear 3:1 against `card-dark` (requiring luminance ≥0.140) and against `brand-dark` (requiring ≤0.098). The solution set is empty — proved arithmetically.
→ **Replaced with a mandatory 2px ring plus 2px surface-coloured offset.** The offset separates ring from button, so the ring only ever needs contrast against the surface. This makes it legible on a brand-filled primary button, the highest-traffic focusable element in onboarding.

## Entry 26 — Amendment (2026-08-23): "no account" becomes "no account required"

Logged after Entry 25 finalized the run, because it changes a Foundation statement both spines were distilled from rather than adding a new one.

- **Superseded:** Foundation's *"One user, one machine, **no account**. No login, no sync, no household sharing. Nothing in this spine may imply otherwise."* That absolute was written before Cognito sign-in existed in the product, and taken literally it forbids the sign-in the product now has.
- **Decision:** the statement becomes *"no account **required**; optional Nixus Cloud identity/sign-in exists, currently gates no local functionality and sends no local profile data."* Local mode still has no login, no sync and no household sharing. Nothing in the spine may imply local mode requires an account, and nothing in it should be read as banning an optional identity.
- **Scope of what Nixus Cloud is, per `architecture-login.md`: identity only.** No cloud data sync, no backup, no notification delivery, no account-based AI service, and no feature gated by login status. An earlier draft of this entry and of Foundation described "additive AI / backup / notification services" and more services over time — **that was invented and is retracted.** The architecture lists cloud sync, push notifications and community features as explicitly deferred, with no infrastructure built; there is no backend compute at all beyond Cognito's own OAuth endpoints.
- **Why this is not a reversal.** Local-first and an optional identity are not competing claims about the same thing. What is still banned is the *unqualified* absolute: no "your data never leaves your machine," no "100% local," no "no server ever" at product level. Feature-scoped no-network claims stay valid and stay put (template exchange remains file-based, no account, no server).
- **Consequence for the spines:** `EXPERIENCE.md` Foundation carries the amended wording in both places it appeared. Nothing else in either spine depended on the absolute.
- **Consequence for the launch surface:** this is what makes a cloud-first picker legitimate.
