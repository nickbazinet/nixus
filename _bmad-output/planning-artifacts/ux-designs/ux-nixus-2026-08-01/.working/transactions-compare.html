Transactions — expenses only vs unified

Both rendered in Direction A "Quiet Ledger" so the only variable you're judging is scope, not style. Both sit at Spending ▸ Transactions as a segmented sub-nav, never as an 11th tab — architecture rule D8.

This is the surface your spreadsheet refugees will look for first. Today it does not exist: ExpenseList only renders nested inside an expanded Budget category row, scoped to one category × one month, with no search, filter, sort, or table markup.

⚠ Historical artifact. Rendered before the computational contrast pass; ink-faint and micro-label sizes here were superseded. DESIGN.md wins on conflict — read token values from the spine, never from this file. Kept as the record of why Variant 1 was chosen.

Variant 1

Expenses only

One row per expense, across every category and every month. Everything a spreadsheet user reaches for — scan, search, sort, filter, bulk-fix — over the data you already have.

✓ Works today

  • Date-range filter
  • Merchant search (LIKE, escaped)
  • Single-category filter
  • Date sort, both directions
  • Limit 1–100 per query

⚑ Small backend adds

  • offset param → real paging
  • Sort by amount / merchant
  • category_id IN (…) multi-select
  • account_id as a filter

✗ Still can't

  • Search notes or category names — merchant field only, no FTS index
  • Show income alongside
  • Show a running balance — no balance history table exists

  1. Search is merchant-only. Honest placeholder — "Search merchants", not "Search". It will not find a category name or a note, and there's no FTS index to make it.
  2. Multi-category needs a trivial IN clause the query doesn't have yet.
  3. Sortable amount and merchant are the two columns a spreadsheet user reaches for first. Neither exists in search_expenses today.

  5. "Load 50 more" is blocked today — limit is clamped 1–100 with no offset. Without it, a spreadsheet user with two years of history can only ever see their most recent 100 rows.
Variant 2

Unified — money out and money in

One list for everything that moved. Closer to how a spreadsheet actually looks, and the only version that can answer "what happened in March?" in a single view.

✓ Reuses from Variant 1

  • Every expense-side filter and sort
  • Same table, same bulk actions
  • Same segmented placement

⚑ Design work it adds

  • Direction filter — All / Out / In
  • A heterogeneous 3rd column: Category for expenses, Source for income
  • Signed amounts, and a real net figure in the footer

✗ Real backend cost

  • search_income does not exist at all — built from scratch
  • Cross-table paging and sorting over two tables with different shapes
  • Bulk actions can't apply uniformly — no "change category" for income

  1. The heterogeneous column is the real design cost. Expenses have a budget_category_id; income has a source_id. They are not the same kind of thing, so one column has to mean two things. The direction glyph plus different tag colours carry it — but it's a compromise, and a purist would say it's two lists wearing one costume.
  2. A net figure is the payoff. This is the one number a spreadsheet actually gives you and Nixus currently doesn't: did more come in than went out? Variant 1 structurally cannot show it. Note this is net flow, not a running balance — no balance-history table exists, so a per-row balance column is impossible in either variant.

My recommendation: ship Variant 1, spec Variant 2's shape now

Variant 1 buys ~90% of the value for ~20% of the work. Four small query params and your spreadsheet refugees get the screen they're looking for. "Where are my transactions?" stops having no answer.

But design the table for Variant 2 from day one — reserve the direction glyph column, name the third column "Category or source" in the spine even while only categories appear, and build the footer as a summary strip rather than a single total. Then unified is a data change, not a redesign. Retrofitting a signed, two-source table onto a single-source layout is exactly the kind of rework that makes people ship neither.

The honest caveat: Variant 1 leaves income visible only on its own Income page, so "what happened in March?" still takes two screens. If a beta tester's first friction report is about that, you'll know Variant 2 is worth the search_income build.

Both variants honour: 1024px minimum width · tabular figures, no code font · 13px floor · Direction A hairline elevation (--shadow: none) · every figure maskable by the hide-values toggle · bulk-select present from the start (the thing the current import review completely lacks).
