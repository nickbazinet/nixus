- (constraint) Inherited from SPEC: no data leaves the machine this pass (any profile); reuse Cognito PKCE flow exactly as-is; demographic /profile (Cognito-sub-keyed) is a distinct concept from 'local profile' and must not share naming; picker is chrome-free, styled, shown every launch unconditionally, no last-used memory; AI-provider/keyring credentials become per-profile.
- (decision) Working mode: Coaching path. Deliverables: ARCHITECTURE-SPINE.md + memlog (primary, build substrate) AND a fuller human-facing solution-design doc rendering at Finalize.
- (decision) Isolation unit: one directory + one full independent SQLite file per local profile ('Dataset'), not a shared file with per-profile schemas/tables. Reuses init_db/MIGRATIONS/backup/danger-zone code unchanged, just re-pointed at a different directory per dataset. User-confirmed after clarifying the 'multiple schema' question raised a real cross-profile-leakage risk that per-file isolation avoids.
- (decision) Code-level term for the new entity: 'Dataset' (LocalDataset struct, datasets.rs, datasets/ dir, dataset_id). Chosen to avoid collision with the existing demographic 'Profile' feature (profile_store.rs, /profile route, Cognito-sub-keyed) and with the unrelated pnpm 'workspace' term already used in this monorepo. User-facing copy stays 'profile' per the SPEC's own vocabulary; only code identifiers use Dataset. All new code stays inside the existing apps/desktop/src-tauri and apps/desktop/src folders -- no new package.
- (decision) Default dataset placement: the existing app_data_dir ROOT itself becomes the Default dataset's directory -- nkbaz-finance.db, the config table, existing keyring service names, and the demographic profiles/ dir are left exactly where they are. Zero file movement on the highest-stakes file in the app (satisfies CAP-2's lossless/no-user-action requirement with the least risk). Every dataset created afterward (CAP-4/5/6) gets a fresh datasets/<uuid>/ subdirectory. Default's dataset_id is the fixed literal 'default', not a UUID.
- (decision) Switch mechanism (CAP-1/CAP-3): in-app hot-swap, no process relaunch. A new datasets.rs owns: registry read/write (atomic, reusing the write_json_atomic pattern already promoted into json_store.rs for profile_store.rs), resolve_dataset_dir(id), and select_dataset(id) which drops the current DbState connection, opens/creates+migrates the target dataset's DB, swaps the Mutex<Connection> contents in place, updates an in-memory active-dataset-id, and emits a dataset:switched Tauri event. Frontend reacts by queryClient.clear() (full clear, not scoped removeQueries, since virtually every query key is dataset-scoped) and navigating to the dashboard. User explicitly framed the UX as feeling like 'logout/login between profiles', not a page reload -- picker is the equivalent of the login screen.
- (decision) Single-source-of-truth registry: app_data_dir/datasets.json lists every dataset ({id, label, kind: local|cloud-linked, cognito_sub?, linked_from?, is_default, created_at}). The picker reads this file only -- it never opens per-dataset DBs or scans directories to render the list, avoiding the cost of opening every SQLite file just to show labels/kind.
- (decision) Bootstrap/migration state machine (CAP-2): on launch, before any UI, check for datasets.json. Missing + legacy nkbaz-finance.db present at root -> upgrade path: write registry with one entry {id:'default', kind:'local', is_default:true}, zero file movement. Missing + no legacy DB -> fresh install: same single Default entry, empty DB created lazily at root on first access. Registry present -> normal read path. Satisfies 'fully automatic, one-time, lossless, no user action'.
- (constraint) AD boundary: every app_data_dir-dependent module (backup.rs, danger_zone.rs, credentials.rs's per-dataset keys, profile.rs) MUST resolve paths via a single active-dataset-context helper in datasets.rs, never call app.path().app_data_dir() directly themselves. This retires the 'independently resolved at 5 call sites, no shared helper' smell documented in brownfield.md and is the mechanism that makes backup/restore/danger-zone automatically scope to the active dataset (SPEC's own assumption) with no per-feature code change beyond the path-resolution swap.
- (decision) Onboarding state (SPEC assumption, confirmed as a consequence not a new decision): db/config.rs's onboarding_completed flag lives inside each dataset's own SQLite file, so it is automatically per-dataset once each dataset has its own DB file (AD consequence of the isolation-unit decision) -- zero additional code.
- (decision) Per-dataset keyring scope for AI-provider keys (CAP-3, constraint): credentials.rs's AI/AWS key storage gains a dataset_id parameter and computes the keyring SERVICE name as 'nkbaz-finance' for the Default dataset (unchanged, so an upgrading user's already-stored AI key keeps working with zero migration) and 'nkbaz-finance-<dataset_id>' for every dataset created afterward. credentials.rs remains the sole module touching keyring_core::Entry.
- (decision) Cognito session scope: stays exactly as today -- ONE global keyring slot (nixus-auth/cognito-session) and the existing SESSION_CACHE singleton, NOT per-dataset. User explicitly deferred true per-account session scoping to a future pass ('when we log with a different [Nixus Cloud] user... but no worries about that yet'). credentials.rs/auth.rs get zero changes to their Cognito plumbing.
- (decision) Cloud-linked sign-in display (CAP-5's 'cloud-linked-but-signed-out, reattaches on sign-in'), resolved WITHOUT any per-dataset session plumbing: a cloud-linked dataset's registry entry statically stores cognito_sub + label(email) at link time. Its signed-in/signed-out badge is derived at read time by comparing that stored sub to whatever the existing global get_auth_session currently reports -- match => shown signed-in (existing sign_out works as today); no match/no session => shown signed-out. User-confirmed.
- (decision) Login/Migrate branching over the SAME unchanged Cognito flow (CAP-4 vs CAP-5): start_login gains a LoginIntent parameter (Login | Migrate{source_dataset_id}), stored in-process alongside the existing PKCE state/verifier across the redirect round-trip. The OAuth mechanics (PKCE, state CSRF check, token exchange, credentials.rs storage) are 100% unchanged -- only handle_auth_callback's post-token-exchange branching differs: Login mode finds-or-creates a cloud-linked dataset by sub and selects it; Migrate mode always creates a NEW dataset, copies the active dataset's DB file into it (reusing export_backup's proven 'wal_checkpoint(TRUNCATE) then fs::copy' pattern) plus its per-dataset AI-provider keyring entries, tags it cloud-linked with linked_from=source_dataset_id, and selects it -- leaving the original dataset entry completely untouched in the registry as CAP-5 requires.
- (assumption) Migrate (CAP-5) copies the source dataset's AI-provider keyring credentials into the new cloud-linked dataset's keyring slot, in addition to the SQLite file. Inferred from CAP-3's framing that AI-provider credentials are part of what's isolated 'per profile', and from wanting the freshly migrated dataset to be immediately usable without re-entering API keys. Flagged for user confirmation during review rather than blocking on another question round.
- (decision) Demographic Profile feature (profile_store.rs, /profile route, keyed by Cognito sub) is UNCHANGED and stays anchored at the global app_data_dir root regardless of active dataset -- it represents 'who is signed in' (a global, not-yet-per-dataset concept per the Cognito-session decision above), not 'which dataset is active'. Resolves the SPEC's own assumption that this feature is orthogonal and unaffected.
- (decision) Picker is a real TanStack route (routes/picker.tsx) rendered chrome-free. Leaning: minimal-diff conditional-shell rendering in __root.tsx (skip sidebar/TopBar/DestinationNav when the matched route declares itself chrome-free) rather than a full pathless-layout-route reorg of every existing route file -- lowest blast radius given no chrome-free template exists today. Full layout-route reorg noted as a future refactor if more chrome-free routes are ever needed. Root-level navigation gate: before rendering anything else, check for an in-memory 'dataset selected this run' flag; if unset, redirect to /picker (no persistence -- satisfies 'no last-used-profile shortcut'). AccountPromptDialog is deleted, not just unmounted -- fully superseded by the picker's own 'Log in with Nixus Cloud' action per the SPEC's own assumption.
- (decision) New IPC command surface (commands/datasets.rs): list_datasets, create_dataset(label?) [CAP-6], select_dataset(id) [the hot-swap], get_active_dataset. Auth-side additions: start_login gains LoginIntent; a small link_or_create_cloud_dataset helper used by both CAP-4 and CAP-5's post-callback branching.
