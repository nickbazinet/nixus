## Findings

### Critical

### High

### Medium
- **M1 — Two AD-8 propagation/feature claims are verified by absence, not by an explicit affirmative statement.** `allow_promotion_codes`/`discounts[]` support (#7) and `client_reference_id`/`subscription_data.metadata` propagation (#16) under Managed Payments both rest on "not listed as removed/unsupported" rather than a Stripe doc saying "this works." These are pre-existing, general Checkout/Subscription fields orthogonal to the Managed Payments feature, so the inference is reasonable — but recommend a throwaway sandbox Checkout Session test (`managed_payments[enabled]=true` + `allow_promotion_codes=true` + `client_reference_id`) before relying on this in AD-6/AD-8 implementation, since Stripe's removed-parameter lists are user-facing documentation, not a machine-verifiable contract.
- **M2 — AD-5's webhook-event enumeration isn't backed by an MP-specific list.** Stripe documents only `checkout.session.completed`/`async_payment_succeeded`/`async_payment_failed` on the Managed Payments setup page (#15). The spine's assumption that standard `customer.subscription.*` and `invoice.payment_*` events apply unchanged is well-supported structurally (MP attaches to the standard `Subscription`/`Invoice` objects per Stripe's SDK changelog) but should be confirmed with a live sandbox webhook listener before AD-5's "closed, named set" is finalized as code.

### Low
- **L1 — `@aws-sdk/client-dynamodb`/`lib-dynamodb` pin (`^3.1118.0`) is ~3 months behind npm latest (`3.1171.0`, published 2026-11-17 vs. 2026-08-25).** Same major version, caret-range compatible, and it's a faithful inheritance of the existing monorepo-wide pin (confirmed present verbatim in four other `package.json` files) rather than an independent claim for this stack — not a currency defect, but worth a `pnpm up` sweep across the workspace at the project's convenience, not specific to billing.
- **L2 — The Stack table correctly declines to hardcode a Stripe API version string.** This review observed the API version drift *live*: one Stripe doc's cached text said "The current version is `2026-05-27.dahlia`" while another page's code example from the same crawl showed `Stripe-Version: 2026-10-28.endive` — illustrating exactly why the spine's "pin at install; verify latest before the first commit" deferral (rather than a number that would already be stale) is the right call. No action needed.
- **L3 — TypeScript (`~5.8.3`) and Vitest (`^3.2.4`) trail current upstream latest (TypeScript 7.0.2, Vitest 5.1.1) by one to two majors.** Verified via `grep` to be the *exact* existing pin across every other app in the Nixus monorepo (`apps/api-account`, `apps/api-bedrock`, `apps/web`, `apps/desktop`, `apps/account`, `packages/shared`) — this is workspace-convention inheritance, not an independently-asserted "verified current" claim, even though the Stack table's header line ("Verified current 2026-11-18") reads as if every row was freshly checked against upstream. Recommend the Stack table note these two rows as "workspace-aligned" (like the DynamoDB SDK row already is) rather than implying independent currency verification.

## Methodology note

All findings above were produced by direct queries against live sources on 2026-11-18: official Stripe documentation (`docs.stripe.com`, `stripe.com/en-ca`), official AWS documentation (`docs.aws.amazon.com`, `aws.amazon.com/kms/pricing`), the public npm registry (`npm view`), and the Nixus repository's own `package.json` files (`grep`) — not from the model's training data and not accepted on the strength of INVESTIGATION.md's prior claims. The one item flagged as deserving a live sandbox test before implementation (M1, M2) is flagged because the official documentation only supports it by omission/structural inference, which this review treats as a lower confidence tier than an explicit affirmative statement, even though no contradicting evidence was found.
