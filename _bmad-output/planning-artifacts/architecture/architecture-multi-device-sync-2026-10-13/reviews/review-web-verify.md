# Web Verification Review — Architecture Spine, Multi-Device Sync

## Verdict

**PASS WITH CORRECTIONS.**

Every version in the Stack table exists and all but one are the current latest release. The two
genuinely load-bearing external assumptions — that `${cognito-identity.amazonaws.com:sub}` is a
stable per-user identifier usable as an S3 key prefix, and that the SQLite pre-update hook fires for
a `DELETE` with no `WHERE` clause — both check out, the second only because of an implementation
detail that is **not** in SQLite's narrative documentation and must therefore be pinned by a test.

Nothing found invalidates the paradigm or any AD. Four corrections change code that would otherwise
be written wrong (S3 conditional-write error codes, `defer_foreign_keys` lifetime, `ValueRef`
lifetime in the hook, `VACUUM INTO` rowid renumbering), and two cost/currency claims are
materially understated. One Deferred item (cross-region identity-pool federation) is now **resolved**
and can be closed.

Counts: **38 VERIFIED**, **4 WRONG / incomplete**, **7 UNVERIFIED** (5 of them doc-silent rather than
doubtful), **2 VERIFIED-against-source-but-undocumented**.

| Claim | Verdict | Evidence | Source |

| Pre-update hook fires for `INSERT OR REPLACE` deletes | **UNVERIFIED by docs — and the adjacent documented behaviour is a warning** | SQLite documents REPLACE's deletions as *exceptional*: "When the REPLACE conflict resolution strategy deletes rows in order to satisfy a constraint, delete triggers fire if and only if recursive triggers are enabled. **The update hook is not invoked for rows that are deleted by the REPLACE conflict resolution strategy. The exceptional behaviors defined in this paragraph might change in a future release.**" That exception is scoped to `sqlite3_update_hook`, **not** the pre-update hook, and the docs say nothing either way about the pre-update hook under REPLACE. The repo's throwaway rusqlite 0.38 test is the only evidence, and it sits one line away from a documented exception that upstream reserves the right to change. **Correction: (1) pin it with a committed regression test, not a throwaway; (2) prefer `INSERT … ON CONFLICT DO UPDATE` or explicit `DELETE` + `INSERT` in Synced tables so capture never rests on undocumented behaviour; (3) note that REPLACE does not increment the change counter, so any capture or reconcile logic keyed off `changes()` is wrong by construction.** | `https://sqlite.org/lang_conflict.html` |
| **F8** Pre-update hook fires for `DELETE` with no `WHERE` | **VERIFIED against primary source — but NOT stated in the documentation** | The docs describe the truncate optimization as skipping per-row work: "When the WHERE clause and RETURNING clause are both omitted from a DELETE statement and the table being deleted has no triggers, SQLite uses an optimization to erase the entire table content **without having to visit each row** of the table individually", and list only `sqlite3_set_authorizer` returning `SQLITE_IGNORE` as a runtime disable — **the pre-update hook is not mentioned.** The source resolves it: in `src/delete.c` the truncate guard is `if( rcauth==SQLITE_OK && pWhere==0 && !bComplex && !IsVirtual(pTab) #ifdef SQLITE_ENABLE_PREUPDATE_HOOK && db->xPreUpdateCallback==0 #endif )`. I confirmed these exact lines (471–478) **both** on `master` (3.55.0) **and** on tag `version-3.53.2`, the version `libsqlite3-sys` 0.38.2 bundles. So with a hook registered, rows are deleted individually and the hook fires. **Corrections: (1) commit a regression test — this is undocumented behaviour that a future SQLite could change without a doc change; (2) record in AD-3 that registering the hook *defeats* the truncate optimization, so `DELETE FROM t` on the UI write connection is O(rows); (3) AD-15's `danger_zone` wipe must explicitly detach the hook (or guard capture) before `WIPE_TABLES`, otherwise the wipe both slows down and produces exactly the "thousands of tombstones" AD-15 says it prevents — the spine specifies the `epoch_reset` message but never says the hook is suppressed.** | `https://sqlite.org/lang_delete.html` §4; `https://raw.githubusercontent.com/sqlite/sqlite/version-3.53.2/src/delete.c` lines 471–478 |
| Pre-update hook fires for FK `CASCADE` deletes | **UNVERIFIED by explicit statement — consistent with docs, confirmed by the repo test** | No page states "FK actions fire the pre-update hook". The docs do establish the mechanism: `sqlite3_preupdate_depth()` "returns 0 if the preupdate callback was invoked as a result of a direct insert, update, or delete operation; or 1 for inserts, updates, or deletes invoked by **top-level triggers**; or 2 for changes resulting from triggers called by top-level triggers". FK actions are implemented internally as trigger programs, so cascade deletes arrive at **depth ≥ 1** — which both explains the observed firing and gives the discriminator. **Correction to AD-12: it only specifies the *apply* side ("hook disabled, nothing re-emitted") and is silent on the *capture* side. Capture must branch on `get_query_depth()`: depth 0 = the author's intent, depth ≥ 1 = a cascade the remote will re-derive from the same parent tombstone. Emitting depth-≥1 children is redundant today and actively diverges the moment any edge changes from CASCADE to SET NULL or RESTRICT (AD-12 has one RESTRICT and four SET NULL edges).** | `https://sqlite.org/c3ref/preupdate_blobwrite.html` |
| **F4** `PRAGMA defer_foreign_keys` semantics | **VERIFIED — with three caveats AD-11 omits** | Verbatim: "When the `defer_foreign_keys` PRAGMA is on, enforcement of all foreign key constraints is delayed until **the outermost transaction is committed**. … The `defer_foreign_keys` pragma is **automatically switched off at each COMMIT or ROLLBACK. Hence, the defer_foreign_keys pragma must be separately enabled for each transaction.** … This pragma is only meaningful if foreign key constraints are enabled." Plus: "**Caution:** Setting `defer_foreign_keys=0` resets the internal foreign-key tracking state … so that it becomes possible to commit the current transaction even if there are foreign key violations." **Corrections: (1) re-issue the pragma inside every one of AD-11's 500-message transactions — it is not a connection setting, and a once-at-open call silently stops working after the first commit; (2) deferral does NOT permit committing with dangling FKs — it only moves the error to COMMIT, so `sync_pending` must be decided *before* commit or the whole 500-message batch rolls back; (3) never set `defer_foreign_keys=0` mid-transaction — that would commit a referentially broken graph silently; (4) the apply connection must set `PRAGMA foreign_keys=ON` (per-connection, defaults OFF) or both the deferral and AD-12's CASCADE policy are inert.** | `https://sqlite.org/pragma.html#pragma_defer_foreign_keys` |
| `VACUUM INTO` is available | **VERIFIED** | Documented command; bundled SQLite is 3.53.2, far past its introduction. | `https://sqlite.org/lang_vacuum.html`; `sqlite3.h` @ v0.40.2 |
| `VACUUM INTO` gives a consistent snapshot of a live DB | **VERIFIED (exact quote)** | "The VACUUM command with an INTO clause is an alternative to the backup API for generating backup copies of a live database… The VACUUM INTO command is transactional in the sense that the generated output database is a **consistent snapshot of the original database**." AD-9's premise holds. | `https://sqlite.org/lang_vacuum.html` |
| **F3** `VACUUM INTO` is otherwise side-effect-free | **WRONG** | "The VACUUM command **may change the ROWIDs of entries in any tables that do not have an explicit INTEGER PRIMARY KEY**." AD-2 deliberately keeps the integer `id` and all 28+ migrations' FK edges as the local identity. If any table's `id` is an implicit rowid, the snapshot — and therefore every freshly bootstrapped computer — gets **different integer ids and silently re-pointed FK edges**, visible only on the new machine. **Corrections: (1) add a schema-guard test asserting every table declares an explicit `INTEGER PRIMARY KEY`; or (2) use the backup API (which copies pages verbatim and cannot renumber) for snapshots — AD-9 already lists it as the alternative, and this finding is a strong argument for preferring it.** | `https://sqlite.org/lang_vacuum.html` |
| → further `VACUUM INTO` caveats for `snapshot.rs` | **VERIFIED** | "The file named by the INTO clause **must not previously exist**, or else it must be an empty file, or the VACUUM INTO command will fail with an error" → generate a fresh temp path, never reuse. "If the VACUUM INTO command is interrupted by an unplanned shutdown or power loss, then the generated output database **might be incomplete and corrupt**" → run `PRAGMA integrity_check` (or at minimum validate the header and a sentinel query) **before** zstd + upload; an undetected corrupt snapshot becomes `snap/LATEST` and poisons every future bootstrap. | → journal mode of the `VACUUM INTO` output | **UNVERIFIED** | The docs do not state the output's `journal_mode`. Low risk: AD-9's restore re-opens and migrates through `db/backup.rs` anyway. Set `journal_mode` explicitly after the swap rather than assuming. | — |
| WAL + a second connection + `busy_timeout` | **VERIFIED — with a material caveat** | WAL "provides more concurrency as readers do not block writers and a writer does not block readers. Reading and writing can proceed concurrently." `PRAGMA busy_timeout = milliseconds` is documented (max 2,147,483,647 ms). AD-11's approach is sound. | `https://sqlite.org/wal.html`, `https://sqlite.org/pragma.html#pragma_busy_timeout` |
| **F10** → the one-writer caveat | **correction** | WAL removes reader/writer contention, **not writer/writer** contention. The spine has two writers on one file: the UI's `ActiveDataset::write` and the sync actor's apply connection. `busy_timeout` converts that collision into latency rather than an error — which means **AD-11's 500-message batch is a UI-write-latency budget, not just a memory budget**, and AD-16's "sync never blocks" is true only of the *network*, not of the write lock. **Corrections: (1) set `busy_timeout` on the UI connection too, not only the sync connection as AD-11 states — otherwise a UI write hits `SQLITE_BUSY` while apply holds the lock; (2) state the batch-size rationale in AD-11 and add it to the Deferred tuning list alongside poll interval.** | `https://sqlite.org/wal.html` §2.2 |
| → `SQLITE_BUSY` still happens in WAL | **VERIFIED** | WAL §9 "Sometimes Queries Return SQLITE_BUSY In WAL Mode": another connection in exclusive locking mode, last-connection WAL/shm cleanup, and crash recovery each return `SQLITE_BUSY`. | → WAL and the dataset directory | **VERIFIED — worth a line in the spine** | "All processes using a database must be on the same host computer; **WAL does not work over a network filesystem.**" Inherited AD-1 lets a dataset live in a user-chosen directory; a dataset placed on a network share, iCloud Drive or OneDrive breaks WAL and therefore AD-11's second connection. **Recommend a startup check, or at minimum a documented constraint, for sync-enabled datasets.** Minor related note: page_size cannot be changed once in WAL mode. | `https://sqlite.org/wal.html` §1 |

## (e) rusqlite pre-update hook API

Verified against the source at the exact tag, `v0.40.2`, `src/hooks/preupdate_hook.rs`
(`https://raw.githubusercontent.com/rusqlite/rusqlite/v0.40.2/src/hooks/preupdate_hook.rs`).
Note: docs.rs does not build rusqlite with `preupdate_hook`, so the rendered `hooks` module page omits
these items entirely — the source at the tag is the authoritative reference, and the spine's
"versions from docs.rs pages" provenance does not cover this API.

| Claim | Verdict | Evidence |
| --- | --- | --- |
| The closure must be `Send + 'static` | **VERIFIED (exact signature)** | `pub fn preupdate_hook<F>(&self, hook: Option<F>) -> Result<()> where F: FnMut(Action, &str, &str, &PreUpdateCase) + Send + 'static`. The crate even ships a `compile_fail` doctest showing that borrowing a local `AtomicBool` is rejected — so AD-3's buffer must be owned or shared via `Arc<Mutex<…>>`, not borrowed. |
| → it returns `Result` | **VERIFIED (not in the spine)** | `preupdate_hook` calls `check_owned()?` and returns `Result<()>`; registration can fail. AD-3's "registers a pre-update hook" needs an error path — likely "refuse to enable sync for this dataset" rather than a silent ignore. |
| Accessor names | **VERIFIED** | `PreUpdateCase::{ Insert(PreUpdateNewValueAccessor), Delete(PreUpdateOldValueAccessor), Update { old_value_accessor, new_value_accessor }, Unknown }`. `PreUpdateOldValueAccessor`: `get_column_count() -> i32`, `get_query_depth() -> i32`, `get_old_row_id() -> i64`, `get_old_column_value(i: i32) -> Result<ValueRef<'_>>`. `PreUpdateNewValueAccessor`: `get_column_count()`, `get_query_depth()`, `get_new_row_id()`, `get_new_column_value(i: i32) -> Result<ValueRef<'_>>`. Column index is `i32`, not `usize`. |
| **F5** values can be buffered as returned | **WRONG** | Accessors hand back `ValueRef<'_>` borrowed from an `sqlite3_value` that SQLite owns, and the C docs are explicit: "**The sqlite3_value that P points to will be destroyed when the preupdate callback returns.**" **Correction: AD-3's "only appends to an in-memory buffer" must deep-copy each `ValueRef` into an owned `rusqlite::types::Value` (and `Vec<u8>` for blobs) inside the callback.** Buffering the `ValueRef` is a use-after-free; the signature's `'static` bound on the closure already forces the right shape, so this is a "get it right the first time" note rather than a latent runtime bug. |
| → the `Unknown` variant | **VERIFIED — needs a policy** | `PreUpdateCase::Unknown` exists for "a different version than what's supported by this library" and `Action::UNKNOWN` maps to it. **AD-3 should treat `Unknown` as "mark the dataset `dirty`" (triggering the reconcile pass it already defines), never as a no-op** — silently dropping it is precisely the divergence AD-3 exists to prevent. |
| → one hook per connection | **VERIFIED, consistent with AD-3** | "At most one preupdate hook may be registered at a time on a single database connection; each call to `sqlite3_preupdate_hook()` overrides the previous setting." AD-3 registers one hook on the UI write connection and AD-11 leaves it off the apply connection — compatible. (`https://sqlite.org/c3ref/preupdate_blobwrite.html`) |
| **F11** → what the hook never sees | **VERIFIED — a real capture hole** | "The preupdate hook **only fires for changes to real database tables**; the preupdate hook is **not invoked for changes to virtual tables** or to system tables like `sqlite_sequence` or `sqlite_stat1`." **Correction: AD-5's registry test asserts that every migrated table is *classified*; it must also assert that no table classified `Synced` is a virtual table (FTS5, rtree, etc.).** A `Synced` virtual table would capture nothing, with no error — the exact silent divergence AD-3 is designed to prevent. `sqlite_sequence` is harmless here since AD-2 keeps integer ids local. |
| → type-safety bonus | **VERIFIED** | The C API makes `sqlite3_preupdate_old` undefined inside an INSERT callback and `sqlite3_preupdate_new` undefined inside a DELETE callback; rusqlite's `PreUpdateCase` enum makes both unrepresentable. Good choice of wrapper. Also, `sqlite3_preupdate_blobwrite()` means a `sqlite3_blob_write()` update is reported as `SQLITE_DELETE` — not reachable through rusqlite's `Connection` API as used here, but relevant if the `blob` feature is ever added for project images. |
