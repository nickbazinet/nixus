# Adversarial Review — Cloud Profile & Web Account Spine

**Verdict:** The spine is coherent at the altitude it was written, but it governs four surfaces that all mutate one entity and it leaves the *seams between them* unruled — so a compliant Lambda story, a compliant desktop story, a compliant local-profile story and a compliant account-app story build incompatibly in 16 provable places, two of which silently destroy or orphan the exact PII the spine exists to protect.

## Method and unit vocabulary

Every finding below names two (sometimes three) units one level down from the spine. Both obey every ADOPTED rule to the letter; they still cannot be assembled.

## CRITICAL

### C1 — AD-7 + AD-9 + AD-8: the first-upload consent flow can never fire for the population it was written for

- **Units:** U5 (desktop-token/scope) vs U8 (first-upload).
- **Divergence.** AD-9 adds `nixus-api/profile` to `COGNITO_SCOPES` (today `"openid email profile nixus-api/ai.invoke"`, `auth.rs:56`) and rules that "a session lacking it is `reauthentication_required`". Cognito's refresh grant cannot add a scope to an existing grant — the codebase already states this (`auth.rs:1174-1183`, `HostedAiAuth::ReauthenticationRequired` doc comment), and `refresh_session` only ever replays `grant_type=refresh_token` (`auth.rs:901-977`). So every pre-upgrade user is `ResolvedSession::Live` / `AuthState::LoggedIn` with a token that the profile authorizer rejects. U5 ships that correctly. U8's trigger is AD-8's *"When the cloud `GET` returns `null` and a legacy document exists"* — but for exactly this population the `GET` never returns `null`; it returns `reauthentication_required`. AD-7 then rules that *"A failed refresh keeps the last copy and is not an error."* Composition: the pre-upgrade user is silently never prompted, their legacy `profiles/<sub>.json` is never uploaded, and nothing on any surface tells them. The one user cohort AD-8 exists for is the one cohort AD-8 cannot reach.
- **Also broken by the same composition:** AD-7's four refresh triggers all degrade to a silent no-op, so a pre-upgrade user's Profile page renders the legacy copy indefinitely with Save enabled (connectivity is fine) and every save fails.
- **Fix — new AD-18 (scope-upgrade surfacing):** `reauthentication_required` is the *one* refresh/save outcome AD-7's "a failed refresh is not an error" does not cover. The Profile page must render an explicit re-sign-in state for it; the AD-8 legacy check must run against the *post-reauthentication* `GET`, and the consent prompt must be reachable from that state. Add a release gate: a test that a session carrying only `ai.invoke` produces a re-sign-in affordance on the Profile page, and that after re-sign-in the AD-8 prompt fires for a legacy document.

### C2 — AD-10 mandates PKCE but never mandates `state`: login CSRF / session fixation on the account app

- **Units:** U9 authorize-request story vs U9 callback story (two sub-units, both compliant).
- **Divergence.** AD-10 enumerates a confidential client, PKCE, the sole callback, cookie attributes, the session table and `Origin` verification on *non-GET* server functions. It never requires an OAuth `state` parameter, an OIDC `nonce`, or any binding of the authorization request to the browser that started it. PKCE protects the code in transit; it does **not** prevent login CSRF. A compliant implementation that keeps `code_verifier` in a server-side map keyed by `state` (or, worse, in a single server-side slot) accepts `GET https://account.nixusapp.com/auth/callback?code=<attacker's code>` forced on the victim's browser and silently signs the victim into the attacker's account — after which the victim types their real name, DOB and income into the attacker's profile. The callback is a GET, so AD-10's `Origin` rule explicitly does not apply to it, and `SameSite=Lax` *does* send the cookie on a top-level GET navigation.
- The desktop already does this correctly and the spine did not carry the rule across: `verify_state` (`auth.rs:324-334`) compares the callback `state` against the single in-memory pending attempt, draws `state` independently of the verifier (`auth.rs:188-204`, "deriving one from the other would let anyone holding the callback URL reconstruct the other half"), and marks a mismatch `recoverable: false`. AD-10 asks the web for strictly less than the desktop already enforces.
- **Fix — tighten AD-10:** the authorization request carries a CSPRNG `state` and `nonce`; both plus the `code_verifier` live in a pre-auth `__Host-` cookie-bound record that is single-use and ≤10 min TTL; the callback rejects a missing or mismatched `state` with a non-recoverable error and rejects an `id_token` whose `nonce` does not match; the session identifier is **rotated** (new cookie value, new row) at the moment of authentication, never upgraded in place. Add to AD-15: a login-CSRF test (callback with a foreign `code` and no matching pre-auth cookie must be refused) and a fixation test (the post-auth cookie value differs from the pre-auth one).

### C3 — AD-6 puts `local-<dataset-id>` inside the `sub` filename namespace, and the existing loader silently discards the result

- **Units:** U6 (local-profile) vs U3 (desktop cloud copy).
- **Divergence.** AD-6 adds `profiles/local-<dataset-id>.json` into the same directory `profile_store.rs` already owns for `profiles/<sub>.json`. Three concrete collisions, all reachable while obeying AD-6 verbatim:
  1. **The namespace is shared, not partitioned.** `validate_sub` accepts any `[A-Za-z0-9_-]{1,128}` (`profile_store.rs:110-125`) — it accepts `local-<anything>`. Nothing in the spine or the code reserves the `local-` prefix. A cloud-copy write under a `sub` of that shape would overwrite a local dataset's on-device demographics, and the two file families are indistinguishable at the filesystem layer.
  2. **Two charset authorities in one directory.** `is_valid_dataset_id` is `[A-Za-z0-9-]{1,128}` (`datasets.rs:156-160`) — it allows uppercase and a *leading dash*; `validate_sub` additionally allows `_`. `profile_store.rs:106-109` states the single-authority property as load-bearing ("one authority, whichever store the subject reaches"); AD-6 breaks it by naming a second validator for files in the same store.
  3. **The loader rejects the new file.** `load_profile` returns `Ok(None)` whenever `profile.cognito_sub != sub` where `sub` is the filename stem (`profile_store.rs:189-192`). `UserProfile.cognito_sub` is a non-optional `String` (`models/mod.rs:1037-1049`). So AD-6's "Both use the same `UserProfile` schema" forces a local document to store `cognito_sub = "local-<dataset-id>"` — a dataset id in a field named for a Cognito subject, which then also means the document, if ever uploaded by any path, carries a bogus identity. If U6 instead writes `cognito_sub: ""`, `load_profile` silently returns `Ok(None)` and the user's local demographics vanish with no error anywhere.
- **Fix — new AD-19 (profile document identity):** `UserProfile` gains a tagged `owner` discriminator — `{"kind":"cloud","sub":"<sub>"}` | `{"kind":"local","dataset_id":"<id>"}` — and `cognito_sub` is retired from the on-disk shape (migrated on read). The filename is derived from the owner, `local-` is a reserved prefix that `validate_sub` must reject, one charset authority validates every name written into `profiles/`, and the filename↔owner integrity check compares the discriminator, not a bare string. Local documents are never a legal upload body: the wire contract in `account.ts` accepts only `kind: "cloud"`.

### C4 — AD-4's `version` field vs AD-8's legacy detection: the detection path quarantines the document it is supposed to find

- **Units:** U1 (Lambda, defines the document shape) vs U8/U3 (legacy detection).
- **Divergence.** AD-4 puts an integer `version` on the PROFILE item and AD-13 makes `account.ts` canonical for it; AD-8 defines a legacy document as *"a `profiles/<sub>.json` without a `version` field"*; AD-6 says the cloud copy is a copy of the cloud document. U1 therefore ships `version: number` as a required field, U3 mirrors it in the Rust wire model ("Rust wire models mirror the TS contract", AD-13), and the copy is deserialized by `profile_store::load_profile`. A legacy document has no `version`, so serde fails → `load_profile` calls `quarantine_corrupt_document`, **renames the user's only copy of their DOB and income to `<sub>.json.corrupt`**, and returns `Ok(None)` (`profile_store.rs:172-178`, `139-154`). AD-8's "a legacy document exists" check then finds nothing, the consent prompt never fires, and the PII is orphaned under an extension nothing reads. If U3 instead bumps `PROFILE_SCHEMA_VERSION` to 2 (`profile_store.rs:10`), the other arm fires: `load_profile` returns `Ok(None)` on `schema_version != PROFILE_SCHEMA_VERSION` (`profile_store.rs:181-187`) for every legacy document. Either compliant choice destroys or hides the input to AD-8.
- **Fix — tighten AD-4 and AD-8:** on disk, `version` and `upload_declined` are `Option` with `#[serde(default)]` and `schema_version` stays `1` for the lifetime of this spine (a bump is a separate, migrating story). AD-8's legacy detection reads the raw JSON through a dedicated probe that **never** quarantines and never mutates the file; quarantine is reachable only from an explicit repair path. Add to AD-15: a test that a v1 legacy document survives a full launch → refresh → GET-null → decline cycle byte-identical except for `upload_declined`.

### C5 — AD-9's "accessor parameterized by required scope" can silently narrow the stored token and break hosted AI and sync

- **Units:** U5 (new accessor) vs the existing hosted-AI and sync token paths.
- **Divergence.** AD-9: *"`commands/auth.rs` exposes one call-time access-token accessor parameterized by required scope (120 s skew, one refresh-and-retry on `401`). It serves both hosted AI and the profile client."* "Parameterized by required scope" reads naturally as *request a token for that scope*. A compliant U5 that passes `scope=nixus-api/profile` on the `grant_type=refresh_token` POST gets back a **narrowed** access token, and `resolve_session`/`refresh_session` unconditionally re-store the refreshed session into the keyring (`auth.rs:1009-1012`, "this overwrites it rather than creating a second one"). The single machine-wide session slot (`credentials.rs:599`, deliberately not per-account, not per-scope) now holds a token without `ai.invoke` → `access_token_has_hosted_scope` fails (`auth.rs:1167-1171`) → hosted AI reports `ReauthenticationRequired` for every premium user after their first profile fetch. The spine also overlooks that there are already **two** accessors with different token types, not one: `hosted_ai_token()` returns the access token (`auth.rs:1188-1190`) and `sync_id_token()` returns the *id* token (`auth.rs:1260-1262`), plus `refresh_hosted_ai_token()` for the 401 retry (`auth.rs:1195-1211`). "One token path per scope" does not describe the thing it is consolidating.
- **Fix — tighten AD-9:** the accessor never narrows a token request; it always requests the full `COGNITO_SCOPES` set and the scope parameter is a **verification** of the granted `scope` claim, nothing more. A refreshed session may never replace a stored session with one whose granted scope set is a strict subset. AD-9 must also name the three existing entry points it consolidates (`hosted_ai_token`, `refresh_hosted_ai_token`, `sync_id_token`) and state that `sync_id_token`'s id-token path is out of scope for the unification. Add to AD-15: a test asserting the stored session's `scope` claim after a profile-triggered refresh still contains `nixus-api/ai.invoke`.

### C6 — "Delete everything" is both too wide on disk and a no-op in the cloud, and the next launch undoes it

- **Units:** U7 (dataset-lifecycle / danger zone) vs U3 (cloud copy refresh) and U6 (local documents).
- **Divergence, two halves, both from compliant stories:**
  1. **Too wide.** `delete_all_profiles` is `remove_dir_all(profiles/)` on the *global* root (`profile_store.rs:450-458`, called at `danger_zone.rs:95-99`) — chosen deliberately because "a `*.json` glob would leave `.json.corrupt` and `.json.tmp` PII behind". Once AD-6 puts `local-<dataset-id>.json` in that same directory, a "delete everything" run from local dataset A destroys **dataset B's demographics while dataset B still exists**, plus every other `sub`'s cached copy and every `sub`'s row in `avatars.db`. `danger_zone.rs:37-39` documents the intent as "that PII belongs to the person rather than to a dataset" — true for a `sub`-keyed file, false for a dataset-keyed one. AD-7 ("removed by delete-all") and AD-6 ("deleted with that dataset") each describe one file family and neither constrains the blast radius.
  2. **A no-op where it matters, then self-reversing.** Under AD-1 the cloud is the sole source of truth and account deletion is explicitly Deferred. So "delete everything" leaves name, DOB, income bracket, location and avatar in DynamoDB, and AD-7's *"refreshed on signed-in launch"* re-downloads all of it and rewrites `profiles/<sub>.json` on the very next launch. The user's deletion is visibly undone within seconds, and AD-16's legal gate covers only the README/Privacy/Terms wording about *where* data is stored, not this.
- **Fix — new AD-20 (deletion scope matrix):** state, per store, exactly what each of the five lifecycle events removes — sign-out, account switch, dataset delete, delete-all, migrate — and bind it to a test matrix. Specifically: delete-all removes the active dataset's `local-<id>.json`, the signed-in `sub`'s copy and avatar row, and nothing belonging to another dataset or another `sub`; a post-delete-all refresh is suppressed until the user is told, in the confirmation UI, that their Nixus Cloud profile is not deleted by this action and names the (deferred) path that does delete it. AD-16's legal gate must cover that sentence.

## HIGH

### H1 — AD-6's resolver contradicts the structural property `commands/profile.rs` is built on

- **Units:** U6 (resolver) vs U3 (cloud profile commands).
- **Divergence.** Every profile command resolves the subject *before* the directory, and that order is load-bearing by design: *"Both commands resolve the `sub` BEFORE the directory, so 'a no-session call touches no file' is structural rather than incidental"* (`commands/profile.rs:26-31`, `34`, `52`, `90`, `164`, `175`). AD-6 inverts the order — the resolver maps the *active dataset* to a source, and for a local dataset there is no subject to resolve at all. A U6 that keeps the existing order ships local demographics that are unreachable: `get_user_profile` on a local dataset returns `Err(AppError::Auth)` from `current_subject()` (`auth.rs:1109-1116`). A U6 that resolves the dataset first opens the OS secure store and can POST a Cognito refresh for a profile that has no account — the single thing `useProfile.ts:76-81` and `useAuth.ts:50-55` both explicitly forbid. The frontend compounds it: `/profile` renders `SignInRequired` unless the session is `LoggedIn` (`routes/profile.tsx:77,84`), so the local-demographics feature has no reachable surface, and `useUserProfile()` has no `enabled` guard precisely because that gate was assumed (`useProfile.ts:13-14`).
- **Fix — tighten AD-6:** the resolver's *local* branch must be reachable with no session and must never call the subject resolver; the *cloud* branch resolves the subject first and remains the only one that may touch the keyring. State that `/profile`'s gate becomes "cloud-linked and signed-in **or** local dataset", and that `useUserProfile` gains an `enabled` derived from the resolver's answer rather than from the session.

### H2 — AD-6's resolver has no owner cross-check, and the session is machine-wide

- **Units:** U6 (resolver) vs U7 (dataset lifecycle).
- **Divergence.** The Cognito session is a single machine-wide keyring slot, not per-account (`credentials.rs:599`, `credentials.rs:65-66`), while `profiles/<sub>.json` and `avatars.db` are `sub`-keyed. `select_dataset_now` is explicitly the "trusted internal seam" with **no** authorization check (`commands/datasets.rs:275-277`), and startup's auto-select of Default and the post-OAuth `activate()` both call it directly (`cloud_link.rs:93-101`). AD-6 says the resolver "maps the active dataset to its source" but never requires that, for a cloud-linked dataset, the resolved subject equals the dataset's own owner. A compliant resolver that keys off `current_subject()` alone renders account A's name, DOB, income and face while a *Local* dataset — or a second account's dataset reached through the trusted seam — is open. The exact comparison already exists and is already the right one: `is_signed_in` (`commands/datasets.rs:489-493`).
- **Fix — tighten AD-6:** the resolver's cloud branch must require `current_subject() == active_dataset.cognito_sub` (reuse `commands::datasets::is_signed_in`, do not re-derive), and must return "no source" rather than another subject's file on a mismatch. Add to AD-15: a desktop cross-account test — with A's session in the keyring and a Local or B-owned dataset active, no byte of A's profile or avatar is returned by any command.

### H3 — AD-5's 64 KiB avatar ceiling is enforced against a base64 body: every maximum-size avatar is rejected

- **Units:** U1 (Lambda ceilings) vs U4 (desktop avatar) vs U10 (account-app avatar).
- **Divergence.** AD-4 fixes the stored derivative at "256 px, ≤ 64 KiB, same contract as `avatar_store.rs`" — and that contract is exactly 65 536 bytes (`projects/image.rs:38`, `MAX_PROJECT_THUMBNAIL_BYTES = 64 * 1024`), enforced by a named SQLite CHECK (`avatar_store.rs:98`). AD-5 then sets "byte ceilings of 16 KiB for the profile body and 64 KiB for the avatar". The desktop's existing avatar wire shape is base64 (`UserAvatar.image_base64`, `models/mod.rs:1070-1074`), and AD-13 makes `account.ts` canonical for "avatar payload" without specifying the encoding or which artifact the ceiling measures. A U1 that enforces 64 KiB on the request body rejects every derivative above ~48 KiB, because base64 of 65 536 bytes is 87 384 characters before JSON framing — `payload_too_large` on a file the device just proved acceptable, with no diagnosis available to the user. A U10 that uploads binary `multipart/form-data` and a U4 that uploads base64 JSON are then two incompatible wire shapes for one entity under one AD-13 contract.
- **Secondary, same pair:** nothing fixes the *filename*. A U10 using `FormData` sends the user's original filename; AD-12's loggable list ("`sub`, route, status, latency, error code, byte sizes") neither permits nor forbids it, so it lands in access logs — and the README promises Nixus does not record file names for hosted AI, which users will read as a general property.
- **Fix — tighten AD-4/AD-13:** one encoding on every surface — `{"mime_type": "...", "data": "<base64>"}` — the 64 KiB ceiling measures **decoded** bytes, and a separate explicit request-body ceiling (96 KiB) covers the encoded form. No surface sends a filename in a body, a path or a query, on any route.

### H4 — AD-4 separates the AVATAR item to avoid loading bytes, then provides no staleness signal for it

- **Units:** U3 (profile refresh) vs U4 (avatar cache).
- **Divergence.** AD-4's stated purpose for `sk = AVATAR` is "Prevents: Avatar bytes loaded with every profile read", and it gives that item its own `version`. AD-7 then defines four refresh triggers for "the cloud copy" and says the avatar cache "keeps today's lifecycle", but never says whether the avatar is refreshed, nor how a device decides it needs to be. `GET /` returns the profile only, and the device's avatar store has `uploaded_at` but no version or etag column (`avatar_store.rs:92-102`). A U3 that refreshes only the profile leaves an avatar changed on the web stale on the desktop forever. A U4 that refreshes the avatar on all four triggers downloads 64 KiB on every launch, every sign-in and every Profile-page open — reintroducing exactly the cost AD-4 was written to prevent.
- **Fix — tighten AD-4/AD-7:** `GET /` returns `avatar_version: number | null` alongside the profile (bytes excluded, which preserves AD-4's intent). `avatars.db` gains a `version INTEGER` column written only from a server response. `GET /avatar` is issued only when the returned `avatar_version` differs from the cached one. `removeQueries` on identity change still applies.

### H5 — AD-4 leaves "absent `expected_version` against an existing item" undefined: a silent lost update between web and desktop

- **Units:** U1 (Lambda) vs U10 (account-app form).
- **Divergence.** AD-4: *"`PUT` carries `expected_version`. A first write is conditional on `attribute_not_exists(pk)`, a later write on `version = expected_version`."* It never says what an **absent** `expected_version` means when the item *does* exist — and AD-8 requires that absence to be legal ("Accepting uploads it with `expected_version` absent"). A U1 that treats absent as "unconditional put" ships a silent last-write-wins overwrite reachable from any client that saw `null` once; the concrete race is a user with the account app and the desktop both open, both having read `null`, both PUTting with `expected_version` absent — one edit vanishes with no `version_conflict` and no error. A U1 that treats absent as `attribute_not_exists` is correct but then the first-ever save from the account app (U10, which never performs the AD-8 flow) must learn that absent means "create only", which AD-4 never told it.
- **Fix — tighten AD-4:** `expected_version` is **mandatory** in the contract as `number | null`, never omitted. `null` means "create; must not exist" and a `null` PUT against an existing item returns `version_conflict` carrying the server's current `version` — never an overwrite. A non-null PUT against an absent item likewise returns `version_conflict`, not a create.

### H6 — AD-13's `version_conflict` carries no resource, while AD-4 versions PROFILE and AVATAR independently

- **Units:** U1 (Lambda) vs U10 (account-app form).
- **Divergence.** AD-4 gives PROFILE and AVATAR separate `version` integers. AD-13's closed union attaches an extra field to exactly one code (`validation` (+ `field`)) and gives `version_conflict` nothing. AD-14's account-app v1 is one page that edits "profile, avatar" — so a single Submit can produce two independent conflicts indistinguishable on the wire, and AD-7's rule (*"A `version_conflict` reloads and informs the user"*) cannot tell the user *what* to reload or re-apply. A U10 that saves both in one submit and a U10 that saves them as two sequenced requests behave differently on a partial failure, and neither is ruled out.
- **Fix — tighten AD-13/AD-4:** `version_conflict` carries `resource: "profile" | "avatar"` and `current_version: number`. Profile and avatar are never written in one operation on any surface; AD-7's reload rule is per resource. Add a contract test per code × field combination.

### H7 — AD-13's new error variant splits one user action across two error types with two frontend narrowings

- **Units:** U11 (contract/error) vs U6 (local home) and U4 (avatar).
- **Divergence.** AD-13 mints `AppError::CloudProfile { code, message, field?, recoverable }` narrowed in `src/lib/appError.ts`. The same user action keeps producing the *existing* variant from other paths: local-home validation goes through "the same Rust validator" (AD-6) which raises `AppError::Validation { message, field }` (`profile_store.rs:197-202`, `250-264`, `339-357`), and local avatar derivation raises `AppError::Validation` with field `user_avatar_unprocessable` (`avatar_store.rs:38`, `53-58`). The frontend's avatar message mapper is hard-gated on the old type — `if (error.type !== "validation") return null` (`appError.ts:440`) — so a server-side `unsupported_media` or `payload_too_large` on the same photo-picker click renders the generic fallback rather than the written avatar copy. One form, two error types, two message catalogs, two EN/FR key sets, and AD-13's own stated goal ("Prevents: generic error fall-through") is defeated by the half it did not name. This is the third code-carrying variant alongside `AppError::HostedAi { code, .. }` and `AppError::Sync { code, .. }` (`error.rs:4-34`), and `reauthentication_required` now exists as a code in two unions with no statement that they mean the same thing.
- **Fix — tighten AD-13:** one error surface per user-visible operation. The resolver-level save returns `AppError::CloudProfile` for **both** homes, with local validation failures mapped into the same closed code union and the same `field` vocabulary; the avatar path maps local derivation failures into `unsupported_media` / `payload_too_large` / `validation(field)` rather than `Validation`. `appError.ts` grows one narrowing and `userAvatarMessageKey` reads it. State explicitly that `reauthentication_required` is the same fact in the `HostedAi`, `Sync` and `CloudProfile` unions.

### H8 — AD-12 forbids what AD-5's validator is specified to produce

- **Units:** U1 (Lambda validation) vs U11 (contract/error).
- **Divergence.** AD-12: *"Never log, and never put in an error message: profile field values…"* AD-5 makes the Lambda the final validation authority for country↔subdivision, brackets and currencies, and AD-13 routes its refusals through `message` + `field`. The existing Rust authority — the one AD-5 says is reused for the local home — echoes the offending value into `message` by deliberate design: `"Invalid country code: {code}"` (`profile_store.rs:256-258`), `"Invalid income bracket: {trimmed}"` (`profile_store.rs:350-352`), `"Invalid state, province, or region code: {trimmed}"` (`profile_store.rs:298-300`), `"Invalid income bracket currency: {normalized}"` (`profile_store.rs:373-375`). Those are all profile field values. A U1 that honours AD-12 returns a message with no value; a U11 that reuses the existing Rust messages violates AD-12; and AD-13's own rule that the desktop "mirrors the TS contract" makes the mismatch silent rather than loud. Nothing in AD-15 gates it.
- **Fix — tighten AD-12/AD-13:** `validation` carries `field` and a stable `reason` enum, never the submitted value; `message` is never rendered raw — the UI resolves an EN/FR locale key from `code` + `field` + `reason`, which also satisfies the Consistency Conventions' locale-parity requirement. Narrow AD-12 explicitly: allow-listed reference codes may appear in a `reason`, free-text and identifying values never appear in `message` or any log. Add to AD-15: a test that no `validation` response or log line contains a submitted field value.

### H9 — AD-6's "deleted with that dataset" has no owner, and dataset delete provably cannot do it

- **Units:** U6 (local-profile) vs U7 (dataset lifecycle).
- **Divergence.** AD-6 rules that `profiles/local-<dataset-id>.json` is "deleted with that dataset", and AD-13's inherited invariant keeps the store in the **global root**, not inside the dataset directory. `delete_dataset_at` removes only `datasets/<id>/` recursively plus the registry entry plus that dataset's keyring credentials, and its doc comment states the boundary as an invariant: *"Nothing else on disk is touched"* (`datasets.rs:850-851`, `876-918`). It also refuses to delete the **active** dataset (`datasets.rs:808-812`) and refuses any **cloud-linked** dataset (`datasets.rs:825-829`). So AD-6's rule has no implementer, and the default outcome is orphan PII that outlives the dataset forever — and dataset ids, while random UUIDv4s today (`datasets.rs:256-270`), are not stated anywhere to be non-reusable.
- **Fix — tighten AD-6:** name the owner — `delete_dataset_at` deletes `profiles/local-<id>.json` alongside `credentials::clear_credentials(id)`, as a sibling of the existing precedent — and add a launch-time orphan sweep: any `local-*.json` whose dataset id is absent from the registry is deleted. State that dataset ids are opaque and never reused. Add to AD-15: a test that deleting a local dataset leaves no `local-<id>.json`, and that a hand-added orphan is swept on launch.

### H10 — AD-6's migrate rule strands the user's demographics and silently changes two derived answers

- **Units:** U6/U8 vs U7 (migrate).
- **Divergence.** Migrate does not convert a dataset in place: `migrate_to_cloud_dataset_at` mints a **brand-new dataset id**, copies `nixus.db` into a new directory, and leaves the source Local dataset, its id and its directory entirely intact (`datasets.rs:629-667`, `650`). AD-6 then rules that migration "copies no demographics; the new cloud-linked profile starts empty". Composition: the user ends with a cloud-linked dataset holding all their financial data and an **empty** cloud profile, while their DOB, income bracket and location sit in `profiles/local-<old-id>.json` attached to a dataset they believe they migrated away from. Two derived answers change silently and visibly: the TFSA accumulated-room figure disappears (it is withheld on a missing `birth_date` or `country_code`, `commands/profile.rs:78-84`, `96-99`) and the AI context loses the same fields. The spine solves the identical user need — "demographics I typed are about to become unreachable" — with a consent prompt two ADs away (AD-8) and does not reuse it here.
- **Fix — tighten AD-6:** on the first open of a cloud-linked dataset whose `linked_from` names a local dataset that still has a `local-<id>.json`, offer the AD-8 consent prompt to copy those demographics into the empty cloud profile (once; a decline is recorded in the local file and never re-prompted). The orphan sweep (H9) must not delete a `linked_from` source's document before that prompt has been answered. No consumer may silently change its answer across migration without a user-visible note.

### H11 — AD-10 has no rule for the post-login redirect target: open redirect on the one callback it does name

- **Units:** U9 (callback) vs U10 (deep-linkable profile page).
- **Divergence.** AD-10 fixes the callback to a single URL and says nothing about where the server sends the browser *after* authentication. U10 wanting `/profile` deep links — the obvious v1 need, since AD-14's account app is "sign in, view/edit profile, avatar, sign out" — adds `?next=` or `?redirect_to=` to the sign-in entry and echoes it after the callback. A compliant implementation that validates "starts with `/`" still accepts `//evil.example` (protocol-relative) and `/\evil.example`; one that validates "same host" by substring accepts `https://account.nixusapp.com.evil.example`. With `SameSite=Lax` the session cookie rides the top-level navigation, so the landing page is a credible phishing surface for the account it just authenticated.
- **Fix — tighten AD-10:** the post-authentication destination is selected from a server-side allow-list of same-origin **path constants** keyed by an opaque token stored in the pre-auth record (C2). No request-supplied URL, absolute path, or protocol-relative string is ever echoed into a `Location` header or a client-side redirect. Add to AD-15: a redirect test over `//host`, `/\host`, `https://host`, and a host-suffix lookalike.

### H12 — AD-14's "explicit URL override" sends a Cognito access token to an arbitrary host

- **Units:** U2 (infra/config) vs U3 (desktop profile client).
- **Divergence.** AD-14: *"Local development defaults to the profile API disabled unless an explicit URL override is set."* It does not say the override is debug-only, must be `https`, or must match an allow-listed host. A compliant U3 reads it from an env var or a config file at runtime in all build profiles — and that is a one-variable token-exfiltration primitive: the client attaches a bearer access token carrying `nixus-api/profile` (and, after AD-9, `nixus-api/ai.invoke`) to whatever host the override names. The spine's own AD-9 network-allowlist test constrains *which module* may hold a client (`cloud_link.rs:157-234`), not where it may point.
- **Fix — tighten AD-14:** the override is compiled in only under `#[cfg(debug_assertions)]`, must be `https` with an allow-listed host suffix, and release builds hard-code the production URL. Add to AD-15: a release-profile test asserting no override path exists and that no request is issued to a non-`api.nixusapp.com` host.

### H13 — AD-10's "revokes the refresh token" is unscoped and can sign the user out of the desktop app

- **Units:** U9 (account-app sign-out) vs U5 (desktop session).
- **Divergence.** AD-10: *"Sign-out deletes the row and revokes the refresh token."* It does not say *whose*, or by which API. The desktop deliberately performs no revocation at all — `sign_out` is local-only and synchronous, and the omission is documented as a v1 decision (`auth.rs:1284-1286`, `1289-1318`). A U9 that reaches for `GlobalSignOut` / `AdminUserGlobalSignOut` (both natural reads of "revokes the refresh token", both available on the pool) invalidates the user's refresh tokens **across app clients** — so clicking "Sign out" on the website kills the open desktop session, and because `authorize_selection` refuses a cloud-linked dataset the moment `current_subject()` fails (`commands/datasets.rs:261-272`, `278-295`), the user's dataset becomes unopenable mid-session with no explanation.
- **Fix — tighten AD-10:** sign-out calls `/oauth2/revoke` on the **web app client** for that session's refresh token only. `GlobalSignOut` and `AdminUserGlobalSignOut` are forbidden in this scope. State that desktop and web sessions are independent and that neither surface's sign-out affects the other.

## MEDIUM

### M1 — AD-13 overrides only the authorizer's `GatewayResponses`; throttling and oversize fall through generic

- **Units:** U2 (infra) vs U11 (error contract).
- **Divergence.** AD-13 says "API Gateway authorizer `GatewayResponses` emit the same envelope", and AD-13's own stated purpose is to prevent "generic error fall-through". AD-14 adds a stage throttle and AD-5 adds byte ceilings. A REST API's stage-throttle 429 is the `THROTTLED` gateway response and an oversize body is `REQUEST_TOO_LARGE` — neither is an authorizer response, so both reach the client as API Gateway's own `{"message":"..."}` and land in `appError.ts`'s generic branch. AD-13 defines `rate_limited` and `payload_too_large` codes that nothing emits.
- **Fix:** enumerate every `GatewayResponse` type that must be overridden — `DEFAULT_4XX`, `DEFAULT_5XX`, `THROTTLED`, `UNAUTHORIZED`, `ACCESS_DENIED`, `EXPIRED_TOKEN`, `INVALID_API_KEY`, `MISSING_AUTHENTICATION_TOKEN`, `REQUEST_TOO_LARGE` — and add an AD-15 gate that each returns the envelope with the mapped code. Note also that a stage throttle is API-wide, so with no WAF (AD-14) one abusive `sub` degrades every user; a per-`sub` usage control or a deliberate acceptance belongs in AD-14.

### M2 — AD-5's parity test does not name which Rust constant, and two currency allow-lists exist

- **Units:** U1 vs U6.
- **Divergence.** AD-5: "Bracket and currency allow-lists are declared once in `packages/shared/src/types/account.ts`, and a Rust parity test fails on drift." Rust has two currency allow-lists with different contents and the same conceptual name: `VALID_INCOME_BRACKET_CURRENCIES` (20 codes, `profile_store.rs:80-83`) and `VALID_CURRENCIES` (`["CAD","USD"]`, `db/account.rs:21`). A parity test wired to the wrong one passes vacuously or fails spuriously forever.
- **Fix:** AD-5 names the exact Rust symbol under test and states that `db/account::VALID_CURRENCIES` is a different, unrelated allow-list (account currencies, not income-bracket currencies) that the parity test must not touch.

### M3 — AD-5/AD-6 TOCTOU: the resolver reads the active dataset, and two concurrent switches are not serialized

- **Units:** U6 (resolver) vs U7 (dataset lifecycle).
- **Divergence.** `active_dataset_dir` / `active_dataset_id` read the active id under `DbState`'s lock and return; nothing holds that lock across the caller's file access, and the registry lock and the active-dataset lock are deliberately different locks guarding unrelated invariants (`datasets.rs:135-141`, `74-77`). Two concurrent `select_dataset` calls race to completion in either order, and `is_already_active` only suppresses a re-select of the same id (`commands/datasets.rs:42-44`). A resolver that re-reads the active dataset deep inside the save path can write demographics into the previously-active source. AD-6 gives one resolver but never binds its answer to the activation the caller observed.
- **Fix:** the resolver returns an explicit source token (`{kind, sub|dataset_id}`); that token is passed through the whole operation, is part of the frontend query key, and is re-validated against the active dataset immediately before the file write — a mismatch is an error, never a silent write to the other source.

### M4 — AD-15's cross-account gate covers the API only, and the scope gate has no mirror

- **Unit:** U12.
- **Divergence.** AD-15 gates "user A's token can neither read nor write user B's `PROFILE`/`AVATAR`" and "every profile route rejects a token lacking `nixus-api/profile`". Three compliant-but-unproven holes remain: (a) no desktop cross-account gate (H2's scenario), (b) no account-app gate that a session row cannot serve a profile for a different `sub` than the one that created it, (c) no mirror gate that **Bedrock** routes still reject a token lacking `ai.invoke` now that one hostname fronts two APIs with two scopes and one token carries both (AD-3, AD-9).
- **Fix:** add all three to AD-15. Also add the reverse of AD-11's guard — a CI check that profile-Lambda code references no session table — since AD-11 states the IAM fact but AD-15 gates only one direction.

### M5 — AD-16's in-app disclosure rule leaves the web's point of collection silent

- **Units:** U10 vs U8.
- **Divergence.** AD-16: *"In-app disclosure is the AD-8 consent prompt only."* AD-8's prompt exists on the desktop and fires only for a legacy local document. A user who signs in on `account.nixusapp.com` and types their DOB and income into a brand-new profile sees no notice at the point of collection, and AD-2 guarantees every account can reach that page. AD-16 is formally satisfied by a README/Privacy/Terms change the user may never read.
- **Fix:** the account app's profile form carries a persistent EN/FR storage-location notice at the point of collection (same sentence AD-16 gates in the policies), and AD-16's rollout gate covers its presence.

## LOW

- **L1 — AD-7's lost-response case asserts the wrong fact.** AD-7 ("Save sends the request, awaits success, then rewrites the copy… A `version_conflict` reloads and informs the user") does not cover a PUT that succeeded server-side whose response was never observed. The device keeps `version = N`, the server is at `N+1`, and the next save tells the user someone else changed their profile — about their own successful save. *Fix:* a save whose response is not observed is resolved by a `GET` and a value comparison before the user is told anything; `version_conflict` copy must not assert another actor.
- **L2 — AD-4 composes `pk = USER#<sub>` with no shape rule for the claim.** AD-3 guarantees the `sub` comes from verified claims but nothing constrains its shape before it becomes a partition key, and the desktop's own subject check for the same identity is a broad `[A-Za-z0-9_-]{1,128}` allow-list (`profile_store.rs:110-125`). *Fix:* the Lambda validates the claim against a UUID shape before key composition and returns `unauthorized` otherwise; `pk`/`sk` never appear in any response.
- **L3 — AD-10's 24 h idle TTL is refreshable by an unauthenticated cross-site GET.** With `Origin` verified on non-GET only, any third-party page can keep a victim's session alive indefinitely with an embedded `GET` to the account app. *Fix:* idle TTL is extended only by an `Origin`-verified request; the 7 d absolute cap is never extended.

## What is well-defended (not a finding, stated so the review is falsifiable)

- The **desktop loopback callback** is not CSRF-able: `state` is drawn independently of the verifier, consumed single-use from one in-memory pending attempt, and a mismatch is non-recoverable (`auth.rs:188-204`, `324-334`, `596`). AD-10 should copy this, not weaken it (C2).
- **Cross-account dataset opening** is correctly refused: `authorize_selection` string-compares the registry's immutable `cognito_sub` against `current_subject()`, treats a failed subject resolution as signed-out, and omits both the sub and the dataset id from the message (`commands/datasets.rs:249-272`, `489-493`).
- **Path traversal via `sub` or dataset id** is closed: both allow-lists exclude `.`, `/` and `\` (`profile_store.rs:110-125`, `datasets.rs:156-160`); dataset ids are CSPRNG UUIDv4 and never user-influenced (`datasets.rs:256-270`). The residual risk is namespace *collision*, not traversal — see C3.
- **Token material never reaches a log**: `TokenResponse`, `TokenRefreshResponse`, `CallbackParams` and `PendingAttempt` all deliberately omit `Debug`, and OAuth error codes are sanitized to `[A-Za-z0-9_-]{0,40}` before logging (`auth.rs:172`, `181-186`, `223-228`, `772-774`). AD-12 is consistent with the existing posture for credentials; its conflict is only with field *values* (H8).
- **Dataset-switch and sign-out cache sweeps** are total, not enumerated: `clearProfileScopedState` calls `queryClient.clear()` (`lib/datasetSwitch.ts:19-30`). The residual gap is the `auth:callback-received` handler, which is a hand-maintained four-key `removeQueries` list (`useAuth.ts:65-85`) and is the *only* sweep that runs when a sign-in completes without a dataset change — any new profile-family query key this spine adds must land in it or be covered by a prefix rule. Worth one sentence in the Consistency Conventions row for query keys.
