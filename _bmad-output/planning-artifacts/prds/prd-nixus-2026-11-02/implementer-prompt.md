# Implementer Prompt — AI-Generated Home Dashboard

You are implementing the **AI-Generated Home Dashboard** feature for Nixus (Tauri 2 + React 19 + Rust/SQLite desktop app). Full requirements, rationale, and mechanism detail live in two files — **read both in full before writing any code**:

- `_bmad-output/planning-artifacts/prds/prd-nixus-2026-11-02/prd.md` — the PRD. FR-1 through FR-11 are your acceptance criteria; every FR has a "Consequences (testable)" block — treat those as your test list.
- `_bmad-output/planning-artifacts/prds/prd-nixus-2026-11-02/addendum.md` — mechanism detail: which existing pipeline to extend, how premium gating must bypass the normal BYO fallback, a sketch of the Widget JSON shape, and a note on keeping the generation prompt out of the shared chat system prompt.

## Two decisions already made for you — don't re-litigate them

1. **Nav placement is settled: `/home`, a fourth top-level rail item.** Nixus's `apps/desktop/src/lib/navigation.ts` has a `FourDestinations` type with Finance, Car, and AI occupying three of the four slots; Home takes the fourth. The app's launch route and Finance's current default ("Today" at `/`) are unchanged — Home is additive, not a new launch target. Implement FR-10 exactly as written in §4.5; this is no longer an open question.
2. **This feature is Nixus Cloud premium-only, with no BYO fallback.** Unlike chat/project-advice/trends-insight, Home's generation must never fall back to a user's own configured AI provider on a `premium_required` outcome. Read addendum.md's "Premium-only, hosted-only" section before touching `ai/backend.rs` or any command handler — the eligibility check (reusing `ai/hosted_state.rs`'s existing `is_eligible` logic) must short-circuit to the FR-11 locked state *before* the point where other surfaces consult `fallback_for`, not add a new branch inside `fallback_for` itself (that would change behavior for every other surface sharing it).

## What "done" looks like, FR by FR

Work through these in roughly this order — later ones depend on earlier ones:

1. **FR-1, FR-2 (Component Catalog).** Build the six Display Components and four Layout Primitives per §4.1's "Build-cost honesty" split: Table and Metric are near-reuse (wrap the existing `packages/shared/src/ui/table.tsx` and `Stat`/`SubStat` from `packages/shared/src/ui/stat.tsx`); LineChart/BarChart/AreaChart require extracting series-agnostic, Data-Binding-driven primitives out of the existing bespoke `NetWorthTrendChart`, `SpendingTrendChart`, and `ProjectionChart` — do not just wrap them, generalize them; PieChart is new, built on recharts like the others. Card/Row/Column/Grid are new layout-only components with no Data Binding. Canonical component name is `PieChart`, not `PieChart/Donut`.
2. **FR-3 (Data Source Whitelist).** Implement the seven whitelisted queries (expenses by month, expenses by category, net worth history, budget vs. actual by category, income vs. expense by month, account balances, asset values) as Rust query functions in the existing `db/` layer, each with a name, a description (for the AI prompt), and a typed parameter shape. Critical constraint from FR-3's NFR: **the generation prompt gets only names/descriptions/parameter shapes — never resolved values.** Write the CI-level assertion from §6.1/§4.2 now, early: seed a profile with known data, assert the outbound generation request contains none of those values as substrings. This is SM-2 and it's a regression gate, not an afterthought.
3. **FR-11 (Premium gating).** Build the eligibility check before building generation itself: a signed-in premium account with remaining hosted-AI quota gets a working Composer; every other state (not signed in, not premium, quota exhausted for the period) gets the locked/upsell state, with messaging distinct from FR-7's transient-unavailability messaging. Verify a configured BYO provider has zero effect on a non-premium account's access to this feature.
4. **Surface Validation.** Validate every AI-generated Home Surface change against the Catalog + Whitelist before it reaches a confirmation card: real component names, real data-source names, well-formed params, no literal data value in any `dataBinding`-shaped field (but note: `title` is free text and is explicitly exempt from that check — see PRD §4.2 FR-3's assumption). Per the addendum's "Open mechanism question," validate in Rust before the command returns to the frontend — don't let a malformed response reach a TanStack Query cache.
5. **FR-4, FR-5 (Generation + self-healing retry).** Extend the **confirm-then-persist action pipeline**, not the read-only `tool_call` pipeline — this distinction is load-bearing, re-read addendum.md's "Which existing pipeline to extend" section before touching any chat code. Concretely: add a new `action_type` (e.g. `propose_home_surface_change`) to `ACTION_TYPES` in `apps/desktop/src-tauri/src/commands/chat.rs`, parsed from the existing ` ```action ``` ` fence in `apps/desktop/src/components/chat/ChatMessageBubble.tsx`, mirrored into `CHAT_ACTION_TYPES` in `apps/desktop/src/lib/chatActions.ts` with its own query-key invalidation (a new `home-surface` key). Generation is capped at 2 attempts total (1 + 1 corrective retry on a Surface Validation failure), with a 20-second round-trip budget — exceeding either surfaces the same graceful-failure message, not a spinner. Per the addendum, give the Home Surface generation turn **its own dedicated prompt-construction path** (like `project_advice.rs`'s `build_system_prompt` or `trends_insight.rs`), carrying the Catalog/Whitelist schemas — do not append them to `ai/chat.rs`'s shared system prompt, which runs on every ordinary chat turn.
6. **FR-6 (Conversational add/modify/remove).** Add: new Widget, others untouched. Modify: full replace of the targeted Widget's description, but the Widget's `id` and its layout position are preserved — it's a whole-Widget re-emit, not a field-level patch. Remove: resolve the user's natural-language target against current Widget titles by best-effort match; exactly one match → confirmation card naming it; zero or multiple matches → no deletion, ask the user to disambiguate by title. Every one of add/modify/remove goes through a confirmation card before persisting — there is no silent-and-immediate path.
7. **FR-7 (Graceful degradation, premium users only).** Reuse `AppError::HostedAi`'s existing `recoverable: bool` / `hostedAiIsRetryable` distinction. For an otherwise-eligible premium user, Home must render the last-persisted Home Surface with live data even when hosted AI is transiently erroring/out of quota for the moment — only the Composer's generate/modify ability is affected. Keep this messaging distinct from FR-11's "not premium at all" messaging.
8. **FR-8 (Persistence).** New table for the Home Surface (Widgets + their Catalog Component, Data Binding, and layout position), one row set per local profile. Loading Home resolves every Widget's Data Binding against current data — never a cached/snapshotted value. Budget: full 12-Widget Home Surface resolves in ≤1s against local SQLite. A non-premium account's persisted Widgets (e.g. from a prior premium period) still render normally — only generation/modification is locked.
9. **FR-9 (Audit trail).** Enroll the Home Surface entity in the existing `AUDITED_TABLES` registry (this is a registry addition, not automatic) and route every add/modify/remove through the existing `db/audit.rs` `audit::record` pattern.
10. **FR-10 (Nav).** Wire `/home` as the fourth destination in `navigation.ts`/`AppSidebar.tsx` per the decision above, without changing the existing Finance static dashboard's current behavior, route, or launch-destination status.

## Constraints that apply across all of the above

- **No code execution, ever.** The AI never emits, and Nixus never executes, HTML/JS/SQL/Dart from the model. Everything rendered is one of the six/four catalog primitives, fed by one of the seven whitelisted queries.
- **No new generic AI backend path.** Route through the existing `ai/backend.rs` hosted port for the actual model call — but see the premium-gating decision above: Home's eligibility check happens before the port's own fallback logic would otherwise apply.
- **Widget cap is 12 per Home Surface**, enforced by Surface Validation (overflow is a validation failure eligible for the one self-healing retry, same as any other).
- **Scope is Finance-only, single Home Surface per profile, conversational-editing only, premium-only** — no multi-dashboard, no drag/resize UI, no Car-module data sources, no interactive widgets (filters/pickers/buttons inside a Widget), no BYO fallback in this pass. If you find yourself building any of those, stop — they're explicit v1 non-goals (PRD §5).

## Open items to flag back, don't silently resolve

These are real unresolved questions in the PRD (§8) — if you hit one, stop and ask rather than guessing:

1. Whether the Home Surface's persisted JSON needs special merge semantics under Nixus's existing optional multi-device sync, or rides it unmodified.
2. Whether a "rebuild this from scratch" / full-reset affordance is in scope, or only incremental add/modify/remove.
3. What happens to a persisted Widget when a later release renames/removes the Catalog Component or Data Source it depends on, including for synced devices on different app versions.
4. Exact premium-lapse upsell copy/affordance (in-app purchase flow vs. link-out) — a UX-spec detail, not resolved in the PRD.
